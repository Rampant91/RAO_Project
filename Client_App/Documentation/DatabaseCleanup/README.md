# DatabaseCleanup — очистка дублей титула Form 1.0 / 2.0

## Назначение

В части БД у Master формы **1.0** / **2.0** в `form_10` / `form_20` бывает **больше двух** строк
на один `ReportId` (типично две пары `NumberInOrder` 1 и 2, лишние — пустые шаблоны).

UI и импорт опираются на `Rows10[0]` / `Rows10[1]` после сортировки по Order.
При дублях данные юрлица могут оказаться не в том блоке; конвертер аналитики раньше
копировал все строки в `.RAODB`.

## Правила v1 (`CurrentRulesVersion = 1`)

Безопасная очистка при старте приложения (после загрузки `form_10` / `form_20`, до `ProcessDataBaseFillEmpty`):

| Ситуация на `(ReportId, NumberInOrder ∈ {1,2})` | Действие |
|--------------------------------------------------|----------|
| 1 заполненная + N пустых | удалить пустые |
| все пустые | оставить меньший `Id`, удалить остальные |
| ≥2 заполненных | **ничего не удалять**, запись в лог (conflict) |
| ровно 1 строка / здоровые 2 на Master | no-op |

«Пустая» = все значимые поля пустые или `"-"`.

Строки с `ReportId IS NULL` и `NumberInOrder` ∉ {1,2} не трогаем.

Отдельного «applied version» в файле БД нет: повторный прогон идемпотентен; шаг
запускается снова, только если снова есть **удаляемые** пустые дубли (например после
импорта старых `.RAODB` до стоп-крана).

## Когда срабатывает

1. Есть `ReportId` с более чем 2 строками в Local **и**
2. Planner находит хотя бы один Id к удалению (пустой дубль).

Иначе шаг пропускается **без** пункта прогресса (типичный день аналитика с чистой копией;
также conflict-only Master с двумя заполненными).

Если чистка нужна — в прогрессе: «Проверка данных организаций», один батч `SaveChanges`.

Ошибка очистки **не прерывает** старт (только лог). Резервная копия БД создаётся раньше
по существующему пайплайну.

## Стоп-кран (тот же релиз)

1. **`ProcessDataBaseFillEmpty`** — шаблоны Ord=1/2 добавляются только если строк нет и в navigation, и в `form_*`.Local по `ReportId`.
2. **Импорт `.RAODB`** — перед обращением к `[0]`/`[1]` Master схлопывается до канонической пары
   (`[0]`=order 1, `[1]`=order 2). Политика импорта **жёстче** cleanup: при двух заполненных
   в одном order оставляется лучшая по полноте (вторая в БД не попадает), иначе снова
   занесли бы 4 строки. Startup cleanup в этом случае ничего не удаляет (conflict).
3. **Конвертер выгрузки → `.RAODB`** — пишет ровно 2 строки (общий `MasterTitleRowsSelector`).

## Код

`Client_App/Helpers/MasterTitleRows/`

| Файл | Роль |
|------|------|
| `MasterTitleRowFullness` | оценка заполненности |

| `MasterTitleRowsNormalizer` | схлопывание коллекции при импорте |

## Проверка после прогона (SQL)

```sql
SELECT COUNT(*) AS bad
FROM (
  SELECT "ReportId" FROM "form_10"
  WHERE "ReportId" IS NOT NULL
  GROUP BY "ReportId"
  HAVING COUNT(*) > 2
);
```

Ожидание для типичного бага пустых дублей: `0`.
Могут остаться: conflict (≥2 заполненных), строки с order ∉ {1,2}.

## Вне объёма v1 (закладки)

- Мёртвые Master без `Master_DBId`
- Автоудаление при двух заполненных строках одного order (startup)
- Восстановление `ReportsId`
