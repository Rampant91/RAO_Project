# Проверка парности операций при переводе РВ → РАО (код операции 41)

## Назначение

В программе предусмотрен перевод сведений о **радиоактивных веществах (РВ)** в сведения о **радиоактивных отходах (РАО)** по **коду операции 41**. Перевод выполняется из форм учёта РВ в соответствующие формы учёта РАО. На практике часть источников после перевода «теряется»: запись есть только в форме РВ или только в форме РАО, либо данные в парных строках не сходятся.

**Функция поиска непарных строк** автоматически находит такие расхождения и выгружает их в Excel. Это помогает:

- выявить **потерянные при переводе** источники и операции;
- понять, **где именно** осталась «лишняя» или **отсутствующая** запись;
- опираясь на даты операций и документов в выгрузке, **восстановить хронологию** передвижения источников между формами и отчётными периодами;
- провести сверку **по выбранной организации** или **по всей базе**.

Функция **не заменяет** кнопку перевода по коду 41 и **не исправляет** данные сама — она даёт наглядный отчёт для ручного анализа и доработки отчётности.

---

## Связь форм РВ и РАО

| Форма РВ (источник) | Форма РАО (приёмник) | Содержание |
|---------------------|----------------------|------------|
| **1.1** — ЗРИ | **1.5** — РАО в виде отработавших ЗРИ | закрытые источники |
| **1.2** — изделия из обеднённого урана | **1.6** — некондиционированные РАО | ИОУ |
| **1.3** — ОРИ (отдельные изделия) | **1.6** | открытые источники — изделия |
| **1.4** — ОРИ (прочие) | **1.6** | открытые источники — иные учётные единицы |

**Текущая реализация:** одна команда с двумя режимами — **выбранная организация** и **вся БД**. В обоих случаях сверка идёт по всем четырём направлениям (листы Excel для форм **1.1–1.6**). Перед выгрузкой открывается диалог параметров сопоставления (чекбоксы полей для каждой пары форм). Сопоставление всегда **внутри организации** (межорганизационных пар нет).

---

## Где вызывается

- **Аналитика** → **Выбранная организация** → **«Непарные операции 41 (формы 1.1–1.6)»** — нужна выбранная организация.
- **Аналитика** → **«Непарные операции 41 (вся БД)»** — без выбора организации; обрабатываются все организации, у которых есть хотя бы одна операция 41 в формах 1.1–1.6.
- **Контекстное меню организации** (ПКМ по строке в списке организаций, вкладка «Формы 1») — **Аналитика** → пункт по выбранной организации.

## Как работает проверка

### 1. Параметры сопоставления

В диалоге пользователь выбирает, **какие поля** участвуют в ключе для каждой пары (1.1↔1.5, 1.2↔1.6, 1.3↔1.6, 1.4↔1.6). По умолчанию включены все поля пары, включая **«Код РАО»** — он есть в каждой из трёх пар 1.2/1.3/1.4↔1.6 (`CheckCodeRao12To16` / `CheckCodeRao13To16` / `CheckCodeRao14To16`). Снятие чекбокса исключает поле из **ключа парности** (удобно, если расхождение по одному реквизиту не должно давать «непарную»).

Каждая тройка чекбоксов пары синхронизирована с трёхстостоянием «Выбрать все параметры» (`CheckAll` / `CheckAll12To16` / `CheckAll13To16` / `CheckAll14To16`): все включены → `true`, все выключены → `false`, часть — `indeterminate` (`null`). Поле «Код РАО» участвует в этом трёхсостоянии наравне с остальными.

Снятие галки **не означает**, что поле не читается из БД и не попадает в Excel: оно влияет на сопоставление и на closest-match, а не на состав колонок выгрузки.

### 2. Отбор операций

Из **одной** временной копии БД выбираются строки с **кодом операции 41** в формах 1.1–1.6:

- в режиме организации — прямые запросы к `form_11`…`form_16` по `Reports.Id`, с прогрессом «загружено N строк» на каждую форму;
- в режиме всей БД — сначала список кандидатов (есть хотя бы одна строка 41), затем **постраничная bulk-загрузка** (keyset по `Id`, пакеты по 2000) DTO по всем формам 1.1–1.6; `RepsId` берётся из навигации `Report → Reports` в SQL, затем группировка по org; сопоставление идёт по org в памяти.

**Особый случай формы 1.5:** дополнительно загружаются операции с **кодом 14** (частая ошибка: код получения вместо перевода). Они участвуют как кандидаты при поиске пары для **1.1 (код 41)**. В обратную сторону (1.5→1.1) и в список непарных на листе 1.5 строки с кодом 14 **не** попадают. Чекбокс «Код операции (код 14 для 1.5)» включает код в ключ и closest-подсветку колонки «Код».

При загрузке **1.2** вычисляется постоянный код РАО (`RaoCodeHelper.Form12CodeRao`), при загрузке **1.3/1.4** код РАО вычисляется по радионуклидам и агрегатному состоянию строки (`RaoCodeHelper.ComputeCodeRaoFromForm13/14`); на **1.6** код РАО читается как есть из формы.

### 3. Сопоставление

| Направление | Что сравнивается (при включённых чекбоксах) | Числовой допуск |
|-------------|---------------------------------------------|-----------------|
| **1.1 ↔ 1.5** | код операции; дата операции; паспорт; тип; радионуклиды; зав.№; активность; количество; дата выпуска; документ (вид/номер/дата); ОКПО поставщика/получателя и перевозчика; упаковка (имя/тип/номер). На 1.5 кандидаты с кодами **41 и 14**; обратная сверка и выгрузка непарных 1.5 — только код **41** | активность ±10% |
| **1.2 ↔ 1.6** | дата операции; масса (в тоннах); β- и α-активности (из массы, как при переводе); дата измерения активности (= дата операции на 1.2); документ; упаковка; **код РАО** | масса и активности ±10% |
| **1.3 ↔ 1.6** | дата операции; основные радионуклиды; 4 вида активностей; дата измерения (= дата выпуска на 1.3); документ; упаковка; **код РАО**. Поле **Type** формы 1.3 **не** сравнивается | активности ±10% |
| **1.4 ↔ 1.6** | дата операции; объём; масса (т); основные радионуклиды; 4 вида активностей; дата измерения; документ; упаковка; **код РАО** | объём, масса, активности ±10% |

На стороне **1.6** пара ищется среди 1.2, затем 1.3, затем 1.4 (**приоритет 12→13→14**) теми же предикатами, что и при сверке РВ→РАО. Пул строк 1.6 **общий**: одна запись 1.6 может закрыть **не больше одной** строки среди 1.2/1.3/1.4 (сначала забирают пары 1.2, затем 1.3, затем 1.4). Иначе одна и та же 1.6 могла бы «парно» выглядеть сразу на двух листах РВ.

Оба режима (org и вся БД) используют одно ядро `ComputeOrganizationUnpaired` — на одних и тех же DTO результат совпадает.

**Нормализация** (как в аналитике СНК): регистр, лишние пробелы/спецсимволы, lookalike RU/EN, ведущие нули; для радионуклидов — порядок в списке; для дат — канонический формат. Нормализация кода РАО — общий `NormalizeNumber` (регистр/спецсимволы), без специальной обработки цифр кода.

**Особый случай 1.1↔1.5 — пустые паспорт и заводской номер.**  
Партия может быть внесена как одна строка с количеством 8 или как восемь строк с количеством 1. При совпадении остальных ключевых полей сравнивается **суммарное количество**; в отчёт попадает только нераспределённый остаток.  
Служебные заглушки **«-»**, **«б.н.»** / **«бн»**, **«без номера»**, **«н.д.»** / **«н/д»**, **«нет данных»**, **«прим.»** и аналоги считаются **пустым** номером (как при определении СНК) — и для ветки «без серийных», и при сравнении самого поля паспорта/зав.№.

**Не сравнивается** (поля, которые заполняются/переопределяются при переводе, либо не относятся к парности): ОКПО приёмника на 1.6 (берётся с организации при переводе), subsidy / refine / FCP и т.п. Они могут выводиться в Excel, но на признак «парная / непарная» не влияют. **Статус РАО** (`StatusRao`) в проверке парности не участвует и в Excel не выводится вовсе — это чисто учётный признак формы 1.6, не связанный со сверкой РВ↔РАО.

### 4. Closest-match и подсветка

Для каждой непарной строки подбирается **ближайший** кандидат на другой стороне (взвешенный soft-score по включённым полям, как в проверке приёма-передачи). Результат: `ClosestMatchResult<TField>` / `ClosestMatchHighlight` с кандидатом, картой уровней `FieldLevels` (Exact / Near / Mismatch), `ConfidencePercent` (0–99; 100 не показываем) и exact-картой `FieldMatches` для тестов.

**Реализация.** Перебор вынесен в общий модуль `ExcelExport/Pairing/Shared`:

| Компонент | Назначение |
|-----------|------------|
| `SoftSimilarityCore` | Алгоритмы soft-similarity (даты, паспорт, тип, числа, радионуклиды, упаковка) |
| `WeightedClosestMatchEngine` | Взвешенный перебор unpaired × reference, tie-break по дате и Id |
| `ClosestReferenceIndex` | Набор кандидатов (опциональный индекс по дню операции) |
| `FieldMatchLevel` / `FieldSimilarity` | Уровни Exact / Near / Mismatch и числовой score |

При нескольких непарных строках в org перебор выполняется **параллельно** (`Parallel.ForEach` по unpaired). Сопоставление и closest всегда **внутри одной организации**; в режиме «вся БД» org обрабатываются последовательно (дописывание строк в один Excel).

**Числа: парность vs closest.** В **ключе парности** масса, объём и активности считаются совпавшими при расхождении **≤ ±10%**. В **closest** то же расхождение даёт уровень **Exact** (зелёный). **Near** (жёлтый) — когда расхождение **больше 10%**, но значения ещё «похожи» (вне допуска парности, но близко по порядку). Порядок величины (×10, ×100) тоже может давать Near.

В Excel:
- **зелёный** — точное совпадение (в т.ч. оба прочерка/пусто после нормализации, ±10% для активностей/массы/объёма);
- **жёлтый** — похоже, но не точно (опечатка / перестановка соседних знаков, ведущие нули, хвост даты у номера, тип в скобках, код 41↔14, диапазон зав.№ ↔ одиночный номер при qty = длине ряда и т.п.);
- **красный** — сильное расхождение;
- колонка **«Схожесть, %»** между разделителем и правым блоком.

Для листа 1.6 выбирается лучший профиль среди 1.2 / 1.3 / 1.4 (при равном weighted-score — приоритет 1.2).

**Пустые серийные и количество.** Парность безсерийных партий считается по *сумме* qty внутри группы с одинаковым ключом (включая номер упаковки). В closest-подсветке «Количество» сравнивается **построчно** с ближайшим кандидатом (1↔1 → зелёный, 8↔5 → красный), кроме случая **диапазона зав.№** (см. легенду Excel) — тогда зав.№ и qty могут быть жёлтыми. Иначе при расхождении только упаковки qty ложно казалось бы «не совпавшим».

**Агрегатное состояние ↔ код РАО (1.3/1.4).** Отдельно от карты полей закрытого списка сравнения `ClosestMatchResult` несёт `AggregateStateMatchesCodeRao` (`bool?`) — совпадает ли значение «Агрегатное состояние» строки 1.3/1.4 с **первой цифрой** кода РАО ближайшего кандидата на 1.6 (`RaoCodeHelper.AggregateStateMatchesCodeRao`). В Excel это переводится в `FieldMatchLevel`: **Exact** (зелёный) или **Mismatch** (красный); промежуточного Near нет (как в проверке приёма-передачи). На листах 1.3 и 1.4 подсвечивается колонка «Агрегатное состояние»; на листе 1.6 (профиль 1.3/1.4) — колонка «Код РАО» вместо формального посимвольного сравнения кода.

**Без подсветки** строка всё равно может быть в отчёте: если на другой стороне у организации **нет ни одной** операции 41 для сравнения (или все поля пары выключены в диалоге) — closest-match строить не из чего. Отсутствие зелёного/красного не означает, что строка попала в выгрузку ошибочно.

### 5. Результат и Excel

**Компоновка листа (дву-блочная).** Каждый лист формы (1.1–1.6) состоит из двух одинаковых по структуре блоков колонок, разделённых узкой тёмно-серой колонкой-разделителем:

- **левый блок** («Непарная операция», голубой заголовок) — сама непарная строка;
- **колонка «Схожесть, %»** — индекс похожести выбранного кандидата;
- **правый блок** («Ближайшее совпадение», жёлтый заголовок) — та же структура колонок, но заполненная данными **ближайшего кандидата** с парной формы (пусто, если кандидата нет).

Обе половины имеют одинаковый набор колонок: 7 общих информационных колонок + колонки данных формы:

| Блок колонок | Состав |
|--------------|--------|
| Информационные (общие для всех форм, 7 колонок) | Рег.№, ОКПО, Сокр. наименование, **№ формы**, Дата начала периода, Дата конца периода, № п/п |
| Данные 1.1 / 1.5 (17 колонок) | Код, Дата, Номер паспорта, Тип, Радионуклиды, Заводской номер, Количество, Суммарная активность, Дата выпуска, Вид/номер/дата документа, ОКПО поставщика/получателя, ОКПО перевозчика, Наименование/тип/номер упаковки |
| Данные 1.2 (12 колонок) | Дата, Масса, Бета-/гамма-активность, Альфа-активность, Дата измерения активности, Вид/номер/дата документа, Наименование/тип/номер упаковки, **Код РАО** |
| Данные 1.3 (15 колонок) | Дата, Основные радионуклиды, активности (тритий/бета-гамма/альфа/трансурановая), Дата измерения активности, **Агрегатное состояние**, Вид/номер/дата документа, Наименование/тип/номер упаковки, Код РАО |
| Данные 1.4 (17 колонок) | Дата, Объём, Масса, Основные радионуклиды, активности (тритий/бета-гамма/альфа/трансурановая), Дата измерения активности, **Агрегатное состояние**, Вид/номер/дата документа, Наименование/тип/номер упаковки, Код РАО |
| Данные 1.6 (16 колонок) | Дата, **Код РАО**, Объём, Масса, Основные радионуклиды, активности (тритий/бета-гамма/альфа/трансурановая), Дата измерения активности, Вид/номер/дата документа, Наименование/тип/номер упаковки |

Колонка **«№ формы»** (`FormNum`) хранит в информационном блоке, к какой форме относится строка (например, «1.3»), и явно присутствует в DTO наравне с «Код РАО» и «Агрегатное состояние» — это упрощает диагностику при экспорте / повторном использовании DTO вне Excel-листа. **Столбец «Статус РАО» не выводится** и не входит ни в один из блоков; ранее существовавшая на листе 1.2 фантомная 30-я колонка (без заголовка и данных) убрана — колонки 1.2 заканчиваются на «Код РАО».

Прочее:

- Непарные на стороне РВ и на стороне РАО попадают в выгрузку.
- Если непарных нет (ни у выбранной org, ни по всей БД) — уведомление, файл не формируется.
- Файл **.xlsx**: первый лист **«Легенда»** (пояснения по блокам, цветам и парам форм), затем **«Форма 1.1» … «Форма 1.6»**, реквизиты организации и периода, таблица с автофильтром.
- **Режим одной org:** имя вида `{рег}_{ОКПО}_непарные_операции_41`.
- **Режим всей БД:** один файл `непарные_операции_41_вся_БД` — заголовки листов один раз, строки организаций дописываются подряд (рег.№/ОКПО уже в колонках). Orgs без непарных пропускаются.
- При совпадении имени — суффикс `_1`, `_2`, …

**Прогресс заполнения (`ProgressReporter`).** Throttled-репортер (~300 мс + границы этапов) используется на:

- поиске организаций с кодом 41 (сканирование форм 1.1–1.6 с накопительным числом org, затем загрузка карточек пакетами);
- bulk-загрузке форм 1.1–1.6 (постраничное чтение и число строк на форму, группировка);
- сопоставлении / closest / построчной записи листов.

В режиме всей БД дополнительно: текущая организация (`Рег_ОКПО`) и «Организация *i* из *N*».

Для расчёта активностей 1.3/1.4 при выгрузке нужен справочник **`data\Spravochniki\R.xlsx`** (лист «Лист1»: имя нуклида → код канала α/β/т/у). Загрузка: `TryLoadRDictionary` / `TryLoadRDictionaryFromFile`; кэш сбрасывается через `ResetRDictionaryCache` (unit-тесты). Распределение активности по каналам — `GetActivitiesForExport`. Если файл отсутствует или занят — команда сообщает об ошибке и прерывается.

## Чем помогает на практике

| Задача | Как помогает |
|--------|----------------|
| Найти источник, который не перевели в РАО | Непарная строка на 1.1–1.4 |
| Найти «лишнюю» запись в РАО | Непарная строка на 1.5/1.6 |
| Массовый перевод без серийных номеров | Сумма количества при пустых паспорт/зав.№ (1.1↔1.5) |
| Проверить корректность вычисленного кода РАО | Сравнение «Код РАО» в паре 1.2/1.3/1.4↔1.6 + подсветка агрегатного состояния |
| Сверка перед сдачей | Режим «выбранная организация» |
| Массовый обзор по базе | Режим «вся БД» (один Excel) |
| Увидеть, *чем* строки почти совпали | Подсветка closest-match (два блока «бок о бок») |
| Восстановить хронологию | Даты операции, выпуска и документов в выгрузке |

После исправления данных имеет смысл **повторно** запустить проверку или выполнить штатный **перевод по коду 41**.

## Рекомендации пользователю

1. Перед проверкой завершите ввод операций 41 в формах РВ и перевод там, где он требуется.
2. Непарная строка — повод открыть отчёт и сравнить с парной формой, а не автоматический признак ошибки ввода.
3. При пустых паспорте и заводском номере сверяйте **суммарное количество** по группе, а не только число строк.
4. Если ложные «непарные» из‑за одного поля (в том числе кода РАО) — снимите соответствующий чекбокс в диалоге параметров.
5. Красная «Агрегатное состояние» на 1.3/1.4 или красный «Код РАО» на 1.6 (при профиле 1.3/1.4) — сверьте первую цифру кода РАО с агрегатным состоянием источника.
6. Закройте `R.xlsx`, если он открыт в Excel, перед выгрузкой с формами 1.3/1.4.
7. Строка без зелёной/красной подсветки при пустой парной стороне — нормально (см. п. 4 выше).
8. **Жёлтая** подсветка числа (масса, объём, активность) при непарной строке означает «похоже, но не в допуске ±10% парности» — строка остаётся непарной, closest показывает, насколько близко значение. Одинаковые прочерки и пустые реквизиты (ОКПО, паспорт, упаковка и т.п.) подсвечиваются **зелёным**.

## Ручной smoke-чеклист

1. Организация выбрана → диалог параметров → Excel: первый лист **«Легенда»**, затем **шесть** листов форм (1.1–1.6), на каждом — два блока колонок с разделителем.
2. После штатного перевода 41 идеальная пара → сообщение, что непарных нет.
3. Расхождение документа, массы или **кода РАО** → непарные с обеих сторон + **подсветка** ячеек.
4. Снять чекбокс расходящегося поля (включая «Код РАО») → строки склеиваются в пару.
5. Непарная 1.3/1.4 с агрегатным состоянием, отличным от первой цифры кода РАО ближайшего 1.6, → колонка «Агрегатное состояние» красная; на листе 1.6 (профиль 1.3/1.4) — красная колонка «Код РАО».
6. Отмена в диалоге сохранения файла → без падения, прогрессбар закрывается.
7. Нет или locked `R.xlsx` → понятное сообщение об ошибке (сценарий с 1.3/1.4).
8. **Аналитика → «Непарные операции 41 (вся БД)»** → диалог → прогресс сканирования форм / загрузки строк / `Рег_ОКПО` / «i из N» → один xlsx (или «непарных нет»). На одном листе строки **разных** организаций идут подряд (не перезаписывают друг друга); слева и справа у строки — **одна и та же** организация.
9. Org только с одной стороной 41 (например только 1.1) → строки в отчёте **без** closest-подсветки.
10. Лист «Форма 1.2» заканчивается колонкой «Код РАО» — лишней пустой колонки после неё нет.
11. На листах Excel нигде не появляется колонка «Статус РАО».
12. Колонка **«Схожесть, %»** между блоками: жирный шрифт; зелёный / жёлтый / красный фон по порогам; жёлтая подсветка полей при «похожем, но не точном» совпадении.

## Вне объёма / техдолг

**Сделано (не техдолг):**

- Unit-тесты `R.xlsx` и `GetActivitiesForExport` (`Pairing41RDictionaryTests`).
- Параллельный closest по unpaired (`WeightedClosestMatchEngine`).
- Soft-сценарии 1.4↔1.6 (**S12–S14**), unit similarity (~23 теста).
- Smoke EPPlus с NearFill для форм **1.1–1.6** (в т.ч. 1.4).
- Общий shared-модуль closest (используется Pairing41; TransferReceive пока на своём цикле).

**Остаётся (не блокирует релиз):**

- E2E «кнопка перевода 41 → повторная проверка → непарных нет» на живой Firebird-БД.
- Полный EPPlus dual-block write со всеми колонками и реальными DTO (smoke одной строки на форму уже есть).
- Индекс closest **по дню операции** (`ClosestReferenceIndex`, `filterCandidatesByDate`) — заготовка есть, **выключена** (`false`), чтобы сохранить прежний полный перебор reference; можно включить для ускорения на org с тысячами строк.
- Параллельная обработка **org** в режиме «вся БД» (сейчас последовательно из‑за дописывания Excel).
- Миграция **TransferReceive** на `WeightedClosestMatchEngine` (другая модель кандидатов — индекс по OKPO).
